- 2026-10-18 (day 2): CRASH IN THE USB HOST DRIVER -> fixed (toolkit 20b8505: kernel_bridge.c, kernel_hal.c, kernel.h, ohci.c)
  - Seen once (mouse4, ~145 s, ~60 s into the first mission): "[CRASH] Access violation ... Xbox VA of fault: 0xFFFFFFFF (write)", eax=0xFFFFFFFF, ebx=edx=0x8070E0C0, esi=0x8070FE90, ecx=0x02000921. Guest stack sub_004256CC (0x0042570D) <- 0x004257BE <- 0x0042582C <- 0x00423F5E <- 0x004206D4 <- 0x004211FD <- 0x0041EE46 <- game input 0x0002BA63.
  - What the game thread was doing: submitting a rumble SET_REPORT on the pad's control pipe (ecx = setup bytes 21 09 00 02). XPP's submit (sub_004257C4) raises to DISPATCH_LEVEL (KeRaiseIrqlToDpcLevel through [0x4259E0], KfLowerIrql through [0x4259DC]); sub_004256CC starts the queued transfer through sub_0042532E (the fault is inside it; 0x0042570D is its return). sub_0042532E builds the transfer on ED 0x8070E0C0 from descriptors popped off XPP's free list ([0x534D0C], pop sub_00425264, link at TD+0x14) and writes the 8 setup bytes into the first. That pop returned 0xFFFFFFFF.
  - Who else uses that list: XPP's DPC, which retires completed descriptors and pushes them back (sub_00423F92: TD+8 = 0xFFFFFFFF, TD+0x14 = old head). No lock: XPP relies on a DPC never running while the submit is at DISPATCH_LEVEL, which holds on the console's one CPU.
  - Cause (toolkit kernel, not the OHCI register/descriptor model): the timer thread drained the DPC queue (kernel_drain_dpcs) every 1 ms whatever other threads were doing; it never looked at IRQL. XPP's ISR (sub_0042441E) only queues the DPC, so its DPC ran on the timer thread, concurrently with the game thread's DISPATCH_LEVEL submit. A second, smaller gap: the OHCI thread asked xbox_IrqlBlocksInterrupts() and then called the ISR, so a raise could land in between.
  - Measured with temporary builds that counted instead of waiting: usbrace1 (300 s, ISR gate only): 7757 raises inside an OHCI ISR. usbrace3 (220 s, DPC gate off): 6610 DPC drains started while a guest thread was at DISPATCH_LEVEL, and of the first 4000 raises that landed inside a claimed ISR/DPC, 3504 were the game's main thread (guest stack 0x00F7xxxx, the crash's) inside a timer-thread DPC drain and 231 inside an OHCI ISR.
  - Fix: xbox_IrqlClaimProcessor / xbox_IrqlReleaseProcessor (kernel_hal.c). A host thread about to run an ISR or DPCs claims the processor, then checks the depth; a raise to DISPATCH_LEVEL bumps the depth, then waits while another thread holds the claim. Both steps are interlocked, so either the routine is put off or the raise waits for it. The timer thread claims before draining DPCs and before timer DPCs (only when one is due; a timer that only signals waiters still fires at once) and otherwise tries again next tick; after 2 s without the claim it runs them anyway ("[KERNEL] guest IRQL held for 2 s ...; running DPCs anyway"). The OHCI thread claims instead of check-then-call; its 2 s forced delivery stays. The first 8 waits print "[IRQL] tid N raise (guest esp X) waited for tid M's ISR/DPC"; RECOMP_USB_STATS lines end in raises-waited=N dpc-held=N.
  - First attempt gated only the OHCI ISR (usbfix1-2); re-reading kernel_bridge.c showed the DPCs were no longer inline (the comment above KeInsertQueueDpc still said they were; fixed) and the drain was the real gap.
  - Verified: usbfix11-15, 5 consecutive 300 s gameplay runs (gameplay.ps1, muted, auto pad, RECOMP_USB_STATS=1), each reaching gameplay at ~68 s and running to the 300 s watchdog: no crash. Per run, 4982-5610 raises waited for an ISR/DPC and 8275-11337 DPC drains were put off a tick (1 ms); no 2 s fallback fired. Pad reports 106-109k per run (110.8k in usbrace1), rumble SET_REPORTs 582-4730. Last-20-sample fps 106-125 (usbrace1 103, usbfix1 125): no cost seen.
  - Not covered: the APU (apu_core.c) and vblank (kernel_vblank_tick) ISRs still run without the claim; a guest raise does not wait for them (on the console an ISR may interrupt DISPATCH_LEVEL code, so that is allowed).
